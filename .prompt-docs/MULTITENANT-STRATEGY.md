# Tile38-Plus Strategy Guide: Multitenant Hierarchy & Fleets

This document details the recommended strategy for structuring a multi-tiered real-time tracking application in Tile38. 

## Scenario Overview
You have a hierarchy to model:
1. **Platforms/Companies (Empresa)** - Sells tracking technology.
2. **Clients/Partners (Cliente Final)** - Buys tracking technology; owns the fleets.
3. **Fleets/Groups (Frota)** - Logical groups of vehicles.
4. **Vehicles (Veículo)** - The physical assets being tracked.

Both the **Platform** and the **Client** must be able to:
* Create dynamic geofences (polygons).
* Create global speed limits (no physical boundary).
* Apply rules targeting universally, per-fleet, or per-vehicle.

---

## Strategy 1: Data Modeling in Tile38

### Principle: 1 `Collection` per `System Tenant (Empresa)`
* Do **NOT** use a single collection (namespace) for all companies in the system.
* Do **NOT** create thousands of collections per vehicle or per client, as managing generic webhooks across collections scales poorly.

The ideal breakdown:
```bash
# Company A manages its pool of GPS devices
SET company_A_vehicles <vehicle_uuid> FIELD client "cli_100" FIELD fleet "trucks_north" FIELD speed 55 POINT -23.5 -46.6

# Company B manages its pool (fully isolated in memory)
SET company_B_vehicles <vehicle_uuid> FIELD client "cli_205" FIELD fleet "bikes_south" FIELD speed 23 POINT -23.7 -46.8
```

Every single object tracking packet should always arrive with **routing ID fields**:
1. `client_id` (Who owns the vehicle).
2. `fleet_id` (Which fleet it belongs to).
3. `type_id` (Car, Truck, Motorcycle - optional).

## Strategy 2: Defining Global & Geofenced Rules

With the data modeling defined, rules (Speed Limits and Geofences) are created using `SETHOOK` (Push/Webhooks) or `SETCHAN` (PubSub). 

### Creating the Rules

**1. Rule: Platform-wide Global Limit**
"Company A requires all of its vehicles to never exceed 120km/h."
```text
SETCHAN global_limit_comp_A WITHIN company_A_vehicles FENCE DETECT overspeed SPEEDLIMIT 120 speed BOUNDS -90 -180 90 180
```
*Note: Because there is no `WHERE`, this hits every packet inside `company_A_vehicles`.*

**2. Rule: Client-Specific Global Limit**
"Client 100 requires that its entire fleet never exceeds 90km/h."
```text
SETCHAN global_cli_100 WITHIN company_A_vehicles WHERE client == "cli_100" FENCE DETECT overspeed SPEEDLIMIT 90 speed BOUNDS -90 -180 90 180
```

**3. Rule: Client-Specific Fleet Geofence**
"Client 100 wants an alert if any of its `trucks_north` enter the `Depot` zone OR overspeed (max 40) while inside it."
```text
SETCHAN depot_cli_100 WITHIN company_A_vehicles WHERE client == "cli_100" WHERE fleet == "trucks_north" FENCE DETECT enter,overspeed SPEEDLIMIT 40 speed OBJECT {"type":"Polygon", ...}
```

**4. Rule: Single Vehicle Alert**
"Client 100 wants to know exactly when `vehicle_X` leaves the generic parking lot."
```text
SETCHAN lot_exit_vehicle_X WITHIN company_A_vehicles WHERE id == "vehicle_X" FENCE DETECT exit BOUNDS ...
```

## Strategy 3: The Event Routing Pipeline 

When coordinates bounce off Tile38, Tile38 triggers these hooks/channels rapidly. Your backend receives these events in real-time.

**How does the backend know who the event is for?**
The webhook payload JSON generated by Tile38 embeds **the object ID and the original fields** inside the event.

**Example Webhook Payload:**
```json
{
  "command": "set",
  "hook": "global_cli_100",
  "detect": "overspeed",
  "id": "vehicle_uuid",
  "object": { "type": "Point", "coordinates": [-46.6, -23.5] },
  "fields": { "client": "cli_100", "fleet": "trucks_north", "speed": 95 }
}
```

**Backend Resolution (Microservice):**
1. Backend receives webhook.
2. Checks `hook` == "global_cli_100" (Identifies the business rule).
3. Checks `fields.client` == "cli_100" (Identifies the client to send a Push Notification).
4. Emits WebSocket/Push Notification directly to the app of Client 100 indicating `vehicle_uuid` (Fleet: trucks_north) exceeded 90km/h.

## Performance Summary
- **CPU:** Near-zero overhead. The R-Tree drops bounds math trivially. String equality matching (`WHERE client == "X"`) is a simple memory-pointer check in Go.
- **Memory:** Hooks consume very little runtime memory. Having 50,000 global rules partitioned by `WHERE` statements will use less than 150MB of RAM.
- **I/O:** Ensure webhooks use UDP/gRPC or fast HTTP keep-alive channels. If using pubsub/channels, Redis-like pub/sub is strictly CPU-bound.

## Strategy 4: Tile38 as the Single Source of Truth (SSoT)

In many robust setups, the relational database (PostgreSQL/MySQL) only stores metadata (e.g., driver names, billing info) while **Tile38 becomes the absolute Source of Truth for live vehicle coordinates and telemetry**.

If your backend needs to answer questions like: *"Where are all the vehicles of Client 100 right now?"* or *"Give me the telemetry of Fleet X"*, you should query Tile38 instead of syncing data back to SQL.

### Leveraging the `SEARCH` and `SCAN` Commands

When vehicles are logically separated into Collections (e.g., `company_A_vehicles`), your backend can execute blazingly fast queries using the embedded `WHERE` filters over those `.fields`.

**1. Finding all vehicles of a specific Client:**
"I need the live location and telemetry (speed, fuel, timestamp) of all vehicles owned by Client `cli_100`."
```text
SCAN company_A_vehicles WHERE client == "cli_100"
```
*Tile38 returns an array containing the exact GeoJSON coordinates and all associated fields for each vehicle matching that client.*

**2. Finding all vehicles of a specific Fleet:**
"I need to plot `trucks_north` on the dashboard map."
```text
SCAN company_A_vehicles WHERE fleet == "trucks_north"
```

**3. Geofence/Spatial Querying by Fleet:**
"Which bikes from `bikes_south` are currently within 5 kilometers of the new warehouse?"
```text
NEARBY company_B_vehicles WHERE fleet == "bikes_south" POINT -23.5 -46.6 5000
```
*(This uses the R-Tree to instantly find vehicles geographically near the warehouse, and then filters that result down exclusively to the bikes_south fleet).*

### Maintaining Search Performance
1. **Never use `SCAN` for everything:** If you just want a map of *all* vehicles of a specific collection, `SCAN` is fast. But if you want a *specific geographic area*, use `NEARBY`, `WITHIN`, or `INTERSECTS`. Those utilize the R-Tree spatial index directly and are much faster than scanning entire fleets.
2. **Keep the Fields Lightweight:** The telemetry stored in Tile38 fields (via `.SET`) should be strictly operational data that updates frequently or drives rules (e.g., `speed`, `rpm`, `battery`, `timestamp`, `driver_id`). Static configuration data (e.g., the truck's color, license plate, chassis number) belongs in your PostgreSQL/SQL database and should be merged on the backend frontend-render phase.
3. **Pagination:** If a client has 50,000 vehicles, do not fetch them all at once. Use the `CURSOR` or `LIMIT` arguments natively supported by Tile38's `SCAN` to paginate responses back to the frontend maps.
